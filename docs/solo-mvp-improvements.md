# 单人主线改进与创新计划

更新：2026-09-11。

## 产品范围

用户已在第一阶段下线搭子匹配。当前只推进“选本、工具、档案”，不安排找人、互相点赞、组局、拼车或多人选本。本计划替代旧文档中的社交扩展路线。

目标是让一个用户独立完成：明确本次需求 -> 理解候选的适合点和风险 -> 使用工具记录游玩 -> 形成可修正的体验档案 -> 改善下一次选择。

## 改进方向

### 选本：先约束，再解释

长期口味和“这次想玩什么”分开。长期画像描述用户偏好；本次条件表达人数、可用时长、难度和不可接受内容。当前已实现人数、时长和难度过滤；不可接受内容仍需来源和用户设置完善后再启用。

内容展示分成适合点、风险、未知三部分。没有来源的风险字段显示待确认，规则分不包装成满意概率。目录已支持 2-3 本对比，展示同一套规则下的适合点、冲突、风险和未知信息；改变本次条件后可重新请求候选。

先修正当前标签和时长逻辑，再引入可编辑的硬约束。当前库只有示例内容，真实内容需补版本、来源和审核状态；不自动生成“真实评分”或假装已有授权资料。

### 工具：记录事实，保留推理过程

笔记按事实、推测、待验证组织，保留来源和发生顺序。计时、笔记和草稿应在弱网、切页及重进后恢复。当前笔记和记录已通过个人游玩批次 ID 归属，重玩和不同角色的信息不会混在一起。

AI 提示先帮助整理已知信息，再提示核查方向。每条具体提示关联用户已选择的笔记来源；无来源时承认信息不足。角色和幕权限准备好后再开放更深入的分级提示，不直接承诺模型绝不剧透。

### 档案：区分体验原因，允许修正

整体评分只提供弱信号。当前已将剧本内容、角色体验、DM 和同桌氛围分开，只有用户明确确认的内容评分参与推荐；其他维度先留在档案中，避免把主持或同桌问题误判成剧本类型问题。一次低分不应永久否定整个类型；用户修改/删除记录后，推荐也应重新计算。

档案的价值是帮助下一次决策，优先完成可纠错、可回看、能解释推荐变化，再考虑海报或复杂统计。

1-5 已一次性落地首版。下一步转入内容核验和小规模试用，重点验证条件过滤、对比解释、反馈归因和证据来源是否真的帮助用户做决定。以下工作量为单人开发粗估，内容整理和真实用户招募另计。

| 阶段 | 交付和逻辑 | 验收 | 粗估 |
| --- | --- | --- | --- |
| 1. 内容基础 | 20-30 本可核验资料；风险使用固定编码，记录资料来源、版本、确认时间；区分“已确认无此内容”和“未确认” | 每条风险能追溯；缺失信息不会显示为安全；已撤回资料不进入推荐 | 1-2 天开发 + 内容整理 |
| 2. 本次条件 | 已完成首版：人数、最长时长、难度独立保存，先过滤再排序 | 自动化测试覆盖条件过滤和空结果边界；真实内容核验后再开放更多禁忌 | 已完成 |
| 3. 选本对比 | 已完成首版：目录选择 2-3 本，按同一规则展示适合点、冲突、资料状态 | 自动化测试覆盖上限、冲突解释和清空状态；试用观察是否帮助选定 | 已完成 |

| 5. 证据提示实验 | 已完成首版：输入限制到本人当前批次笔记；输出来源 ID、核查步骤和未知项 | 服务端校验所有权和批次；继续用预设案例评估越界、剧透和来源缺失 | 已完成首版 |

第 2-3 阶段以规则实现。对比的核心价值是把“为什么推荐”和“条件改变后为何变化”呈现清楚，不依赖模型编造理由。第 5 阶段首版已限制在用户笔记来源；角色/幕权限和资料授权方案仍需补齐，单靠提示词无法保证不剧透。

试用先做 5-8 人任务观察，解决明显卡点，再扩大到 30-50 人验证。记录“设置条件 -> 查看候选 -> 对比 -> 选定 -> 实际玩过 -> 反馈”的转化和耗时，分别统计没有合适候选、信息不足与主动放弃。数据量小时以具体失败原因决策，不把少量百分比当成稳定结论。

## 接口演进原则

沿用 `{ code, data, message }`。目录查询采用可选参数区分完整目录与推荐，并增加分页信息；按 ID 的公开详情始终可访问。个人笔记和记录的新增、修改、删除必须校验所有权。AI 按服务端已知数据选择有界上下文。

`GET /api/scripts` 保留数组 `data`，新增 `catalog=1`、`collection=saved|dismissed`、`limit=1..100`、`offset`、`maxDuration`、`players` 和 `occasionDifficulty`；响应增加 `pagination: { offset, limit, total, hasMore, nextOffset }`。新增 `GET /api/selection-context`、`POST /api/selection-context` 和 `GET /api/scripts/compare?ids=1,2,3`。

个人数据新增接口：`POST/GET/PATCH /api/play-sessions`、`PATCH/DELETE /api/scripts/:id/notes/:noteId`、`GET/PATCH/DELETE /api/play-records/:id`。笔记和记录可带 `sessionId`，服务端校验批次属于当前用户和剧本。列表增加相同的分页参数与响应字段。修改采用部分更新，记录不可转移至另一剧本。日期使用有效的 `YYYY-MM-DD`。

`POST /api/ai/evidence-coach` 接收 `scriptId`、可选 `sessionId`、最多 5 个 `noteIds` 和问题；服务端只允许当前用户、当前剧本、当前批次的笔记，返回的来源 ID再次经过白名单过滤。

两个创建接口的 `POST` 接受可选 `clientRequestId`（16-100 位字母、数字、下划线或连字符）。客户端在发请求前将标识和草稿一起保存；同用户、同标识、同原始内容返回同一个资源 ID，内容冲突返回 409。记录修改后重试创建会返回当前记录，删除后重试返回 410，不重新创建。独立请求台账与资源创建在同一个 SQLite 事务中完成，删除资源后保留哈希和 ID，以识别延迟到达的重试；台账不保存笔记或短评正文。

当前评分反馈按每本平均评分聚合，同一标签加入两条中性先验，合计影响最多正负 8 分。整体评分仅作为弱信号，后续再引入由用户确认的体验归因；不把低分直接解释成某个硬雷点。当前避雷仍是显式提醒和降权，硬禁忌筛选需要相应的用户选项后再启用。

AI 日次数包含已准入的请求，失败请求也计入防滥用额度；尚未调用供应商就结束的请求可取消预占。成本为预估准入与实际结算，严格账单上限仍需在供应商侧配置。
